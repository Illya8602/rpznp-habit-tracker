# Специфікація: Habit Tracker API (v0.1)

## 1. Мета та сценарії використання

Система призначена для ведення щоденних звичок, фіксації прогресу та обчислення серій виконання (streaks).
Ключові сценарії:

- Створення звички з розкладом (щодня / дні тижня).
- Фіксація виконання звички за поточну або обрану дату.
- Отримання аналітики виконання та поточної серії.

## 2. Модульна декомпозиція та межі (Component Boundaries)

Архітектура дотримується принципу інверсії залежностей:

1. **HTTP Layer (Router & Controller)**: Приймає запит, валідує payload через JSON Schema, делегує обробку доменному сервісу, формує HTTP-відповідь.
2. **Domain Service (Habit Service)**: Бізнес-правила (валідація дат, перевірка повторного виконання, розрахунок серій).
3. **Repository Interface (IHabitRepository)**: Ізольований контракт сховища даних. Верхні рівні не залежать від реалізації збереження.

## 3. Модель даних та зв'язки (ER)

- **User**: `id (UUID)`, `email (string)`, `created_at (timestamp)`
- **Habit**: `id (UUID)`, `user_id (UUID -> User.id)`, `title (string)`, `frequency (daily | weekly)`, `created_at (timestamp)`
- **HabitLog**: `id (UUID)`, `habit_id (UUID -> Habit.id)`, `completed_at (date)`, `note (string?)`

Зв'язки:

- `User` 1:N `Habit`
- `Habit` 1:N `HabitLog` (унікальний композитний ключ: `[habit_id, completed_at]`).

## 4. Сценарій оновлення даних (Життєвий цикл)

1. Клієнт надсилає `POST /api/v1/habits/:id/logs`.
2. Router валідує формат UUID та дату тіла запиту за схемою.
3. Habit Service звертається до репозиторію для перевірки існування логу за дату.
4. Якщо лог уже є — повертається доменна помилка конфлікту (`AlreadyCompletedError`).
5. Якщо лог відсутній — створюється запис у репозиторії, оновлюється streak, повертається результат зі статусом `201 Created`.

## 5. Аудит залежностей (Топ-3 виключені або ризиковані залежності)

1. **Відмова від Express**: Застарілий транспорт, слабка продуктивність; замінено на Fastify.
2. **Відмова від важких ORM на етапі структури**: Використання інтерфейсу репозиторію замість прямої прив'язки до складного ORM зберігає ізоляцію домену.
3. **Відмова від сторонніх валідаторів без схем**: Fastify використовує нативний компілятор JSON Schema, що виключає дублювання бібліотек валідації.
