# DEFENSE: Завдання 1 (Фундамент і структура застосунку)

## 1. Що і навіщо

Habit Tracker API — це сервіс відстеження персональних звичок та аналізу регулярності виконання.
Мета Завдання 1: закласти інженерні стандарти, налаштувати автоматичні перевірки через Git Hooks, ізолювати шари архітектури та підготувати специфікацію на подальші етапи SDLC.

## 2. Топ-3 розбіжності / зрізані кути проти spec.md

1. **Мережевий сокет Fastify відкладено до Завдання 2**: Згідно зі spec.md архітектура описує Fastify HTTP-сервер, проте на етапі 1 реалізовано каркас ініціалізації додатку, DTO та smoke-тести без запуску мережевого слухача. Це відповідає правилу покрокового SDLC (структура передує імплементації).
2. **Збереження стану не реалізовано в коді**: Контракт репозиторію `IHabitRepository` зафіксовано в архітектурі, але конкретні імплементації відкладено до наступного етапу.
3. **Логування виключно у stdout**: Використано базовий Pino логер без розподілу логів на файлові потоки або зовнішні агрегатори.

## 3. Ключове рішення (ADR)

- Рішення: Використання **Fastify** замість Express.js (детально в `adr/0001-choose-fastify-over-express.md`).
- Аргументація: Наявність нативної валідації схем запитів, висока продуктивність обробки та компонентна ізоляція через систему плагінів.

## 4. Перевірка відтворюваності

- Команда перевірки: `make check`
- Результат перевірки: Успішне проходження Prettier, ESLint, TypeScript `tsc --noEmit` та Vitest smoke-тесту.
- Поточна версія: `0.1.0` (commit SHA фіксується у системі контролю версій).
